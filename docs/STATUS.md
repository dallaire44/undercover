# Status

The UnderCover claims pilot, built from `docs/PLAN.md`, and the agent's harness, built from `docs/PLAN_HARNESS.md`: one run works the queue up to a cap, with a to-do list, a fresh claim agent per claim, the claims manual looked up section by section, and failed claims retried or left for a handler.

## Built

- `backend/`: FastAPI on SQLAlchemy Core. With `DATABASE_URL` in its environment it uses Supabase Postgres through the session pooler, with every table in the `undercover` schema (the connection's search path) and at most 4 connections. Without it, as in the tests, it uses SQLite at `undercover.db` (or the file named by `UNDERCOVER_DB`). Each query is written once for both. On first start it copies the claims, policies, customers and handlers from `data/`. Read operations: `list_claims`, `get_claim`, `get_policy`, `get_claim_history`, `get_instructions` and `list_handlers`. The agents' instructions are `backend/instructions/queue.md` and `backend/instructions/claim.md`, served at `/api/instructions/queue` and `/api/instructions/claim`.
  - `backend/documents.py` splits the policy wording and the claims manual into numbered sections: `list_sections` (the contents of both), `search_documents` (the sections that best match a few words, each with its best line) and `read_section` (one section, headed such as `Claims manual, 9. Repeat claims`). The whole wording is no longer served.
  - The rules raise `backend.errors.NotFound` or `Refused`, which `backend/main.py` answers with 404 and 409; nothing else in the backend knows HTTP.
  - The rules are in `backend/rules.py`. `record_decision` takes approve, decline or refer. A decline or referral is decided with a payout of 0. An approval of $1,000 or less stays in progress until `pay_claim` pays it. An approval over $1,000 waits for sign-off: `pay_claim` is refused with 409 until `sign_off` records a handler. A sign-off doesn't pay: it moves the claim back to in progress for the agent to pay, and the payment records who signed off and when. `record_decision` and `pay_claim` return the claim, and a repeat of the same decision or payment counts as done; a different decision or amount is refused.
  - `backend/payouts.py` holds the payout rules from the Week 2 Day 1 lab. `calculate_payout` (`POST /api/policies/{policy_id}/payout`, with the benefit, the lines and what others paid) returns the calculation step by step, the payout and whether it needs sign-off, with the limit from `data/company.json`.
  - `add_step` and `list_steps` keep the agent's steps on a claim.
  - `backend/runs.py`: a run works the queue up to a cap of claims. `take_claim` moves a waiting claim into the run and in progress, with a new `thread_id` for the attempt, and refuses past the cap; a claim the run returned stays in the run, so its retry does not use up the cap. `return_claim` follows a failed attempt: attempts plus one and the thread cleared, then back to `waiting`, or `needs_handler` after two. `write_todos` replaces the run's to-do list (to do, in progress, done, left for a handler). `finish_run` refuses while a claim of the run is in progress or `list_claims_to_work` is not empty. `get_run` and `get_latest_run` read runs. One run at a time. On startup the backend stops any run left running and returns its claims in progress.
  - `backend/runner.py`: `start_run` (`POST /api/runs`, with a cap) and `start_agent` on one claim (a run with a cap of 1) create the run and hand it to the agent's service in a background task. A run the service never takes is stopped with "The agent's service could not be reached." `stop_run` lets the agent stop a run it could not finish, which returns the run's claims in progress. A restart of the backend no longer touches runs or claims: the agent carries on its own work.
  - `backend/agent_service.py` is the backend's only way to the agent, at `UNDERCOVER_AGENT` (or `http://127.0.0.1:8002`). A sign-off asks it to resume the claim once the sign-off is saved; the sign-off stands if the agent can't be reached.
- `agent/`: the UnderCover Agent. The claim agent is a hand-written LangGraph graph and the queue agent is LangChain's `create_agent`, both on OpenRouter and both saved after every step.
  - `agent/api.py` is the only way to the backend: one function per operation, with the base URL (`BACKEND_URL`, or `http://localhost:8000`) in one place. A 4xx raises `api.Refused`.
  - `agent/tools.py` holds every tool. The claim agent's eight each make one backend call, including the three document lookups and `calculate_payout`; it has no tool to pay. The queue agent's four, `list_claims_to_work` (headed with how many more claims the cap allows), `write_todos`, `work_claim` and `finish_run`, reach the run id through `ToolRuntime` context (`context_schema=RunContext`).
  - `agent/harness.py` holds the model, `deepseek/deepseek-v4.1-flash` with low reasoning effort, or `MODEL_NAME` if set, and the claim agent's graph:
    - The nodes are `agent` (the model, with `RetryPolicy` retrying a failed call twice, and a count that raises past 30 model calls), `tools` (a `ToolNode` that hands a refused backend call back to the model as text), `check` (reads the claim back after `record_decision`), `sign_off` (waits on `interrupt()`) and `pay`.
    - After a decision the backend's status decides the way: `awaiting_sign_off` waits at `sign_off`, an approval in progress goes to `pay`, a decline or referral ends. The graph never compares a payout with the limit.
    - Every message, tool call and tool result is a step on the claim, and so are "Waiting for a handler's sign-off.", "Signed off by …" and "Paid $…".
  - The checkpointer is LangGraph's `PostgresSaver` on a pool of at most 4 connections in the `undercover` schema when `DATABASE_URL` is set, and `InMemorySaver` otherwise. Every run uses `durability="sync"`. A claim's thread is its attempt's `thread_id`; the queue agent's thread is the run id.
  - `run_claim(claim_id, thread_id)` starts a thread, carries on one stopped partway from its last step, or resumes one waiting for a sign-off once the sign-off is recorded. `work_claim(run_id, claim_id)` takes the claim (or carries on one the run already holds), posts "Agent started", runs it, and posts "Agent finished" once the claim has left `in_progress`; otherwise, or if it raised, it calls `return_claim`, so the next attempt starts afresh on a new thread. It always answers in one line, such as `CLM-1001: approved, $420.00 paid`. `carry_on()` carries on every claim left in progress, and `run_queue(run_id)` resumes a stopped queue run from its checkpoint.
  - Every claim agent is traced in Langfuse when `LANGFUSE_PUBLIC_KEY` is set, in a session named after the claim and its thread, such as `CLM-1001 ac703c9a-…`, which holds the traces from before and after a sign-off. Nothing loads `.env` in code: `npm run dev` and `npm run reset` pass it with `uv run --env-file .env`.
  - `agent/service.py` is the agent's service and its entry point, a small FastAPI app on port 8002 that `npm run dev` starts beside the backend and the dashboard. `work_run`, `work_one` and `resume_claim` answer 202 and do their work in the background; every run first carries on each claim left in progress. When the service starts, it sets up the checkpointer's tables, waits for the backend, and carries on the run left running, or else the claims in progress.
  - The instructions, `backend/instructions/queue.md` and `claim.md`, give each agent a goal, its rules and what done looks like, not a fixed order of work. The claim agent's work ends with its decision; the system pays.
- `dashboard/`: React, Vite and TypeScript in the UnderCover brand. The queue page has a count of claims in each state and the eight-column table. A claim page, opened from `#/claims/CLM-1001`, shows the summary, the decision and payment, the story, items, documents, policy and claim history. Light and dark start in the computer's setting. The "Dark mode" slider in the header, on every page, switches them and the browser remembers the choice (`localStorage` key `undercover-theme`); the mode is the `data-theme` attribute on `<html>`, set by a script in `index.html` before the page draws. `src/api.ts` holds the typed fetch functions.
  - The queue page's "Agent run" panel (`RunPanel.tsx`) has "Claims to work" (starting at 5) and "Work the queue", disabled while a run is running. It shows the latest run: "Running, up to 5 claims", "Finished, 3 claims worked" or "Stopped" with the reason, its to-do list with a chip per item (To do, In progress, Done, Left for a handler), and the summary once finished. It polls every two seconds while the run is running. The counts and chips include "Needs a handler".
  - A waiting claim has a "Run the agent" button. The claim page shows "Sections read", the first line of each `read` step such as "Claims manual, 9. Repeat claims" ("None yet." before any), and the agent's steps as a timeline (long tool results and sections read fold away) and polls every two seconds while the claim is in progress; the queue polls every two seconds.
  - A claim waiting for sign-off shows a "Payment on hold" panel with a handler picker and "Sign off and pay". Once paid, the decision panel shows the payment with its date and time and who signed off.
  - The "Color-blind mode" slider next to "Dark mode" switches the claim-state, decision and payment-on-hold colors to the Okabe-Ito palette and adds a check, cross or arrow to each decision chip (`data-colors` on `<html>`, key `undercover-colors`, off by default). The two sliders are independent. See `docs/ACCESSIBILITY.md`.
  - `#/instructions` shows the agent's instructions, read only, in two panels: "Running the queue" and "Working a claim".
- `e2e/`: Playwright tests on their own backend (port 8001, `e2e/e2e.db`, rebuilt by `backend.seed` at the start of each run) and their own Vite (port 5174), so they never touch the data from `npm run dev`. Their backend's `UNDERCOVER_AGENT` is a stand-in for the agent's service on port 8003, `e2e/agent-stand-in.mjs`, which answers 202 and lists what reached it at `/calls`; the tests act as the agent through the API.

## Claim states

| State | Meaning |
|---|---|
| `waiting` | In the queue, not yet worked |
| `in_progress` | The agent is working on it |
| `awaiting_sign_off` | Approved over $1,000; payment on hold until a handler signs off |
| `decided` | Declined, referred, or approved and paid |
| `needs_handler` | Failed twice; left for a handler |

## Running it

- `npm run dev` starts the backend (8000), the agent's service (8002) and the dashboard (5173), passing `.env` to the backend and the agent.
- `uv run -m agent --cap 5` starts a run capped at five claims and `uv run -m agent --claim CLM-1001` a run on one claim, both through the backend's API, which hands them to the agent's service, so `npm run dev` must be up. Each prints the to-do list as it changes, then how the run ended.
- `npm run reset` rebuilds the database from `data/`, on Supabase when `.env` has `DATABASE_URL`, where it drops the whole `undercover` schema, the agent's saved threads included: all 25 claims waiting. Stop `npm run dev` first. Run it once after pulling this build, since the tables changed.
- `npm run check` runs every check. `agent/tests/test_structure.py` and `backend/tests/test_structure.py` check the layout in `docs/CODE_STANDARDS.md`.

## Last live run

After the agent was rebuilt as `api`, `tools` and `harness` with goal-based instructions, and a reseed, a run capped at five claims on `deepseek/deepseek-v4.1-flash` worked CLM-1001, CLM-1008, CLM-1010, CLM-1011 and CLM-1018 in about two minutes, with the same decisions as before the rebuild: three approved (CLM-1001 paid $420.00; CLM-1008 $2,240.00 and CLM-1011 $1,150.00 waiting for sign-off, each after its payment came back refused as text), CLM-1010 declined and CLM-1018 referred, with no failures. The other 20 claims stayed waiting. Each claim agent read 8 to 12 of the 26 sections. A first run marked the referral "left for a handler" on the to-do list; `queue.md` now says that status is only for a claim that failed twice, and the second run marked it done.
