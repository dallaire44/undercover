# Status

The UnderCover claims pilot, built from `docs/PLAN.md`, and the agent's harness, built from `docs/PLAN_HARNESS.md`: one run works the queue up to a cap, with a to-do list, a fresh claim agent per claim, the claims manual looked up section by section, and failed claims retried or left for a handler. Then durable state, built from `docs/PLAN_DURABLE.md`: the payout rules in the backend, Langfuse tracing, our records on Supabase, a claim agent that waits for a sign-off and carries on after a stop, and the agent in a service of its own.

## Built

- `backend/`: FastAPI on SQLAlchemy Core. With `DATABASE_URL` in its environment it uses Supabase Postgres through the session pooler, with every table in the `undercover` schema (the connection's search path) and at most 4 connections. Without it, as in the tests, it uses SQLite at `undercover.db` (or the file named by `UNDERCOVER_DB`). Each query is written once for both. On first start it copies the claims, policies, customers and handlers from `data/`. Read operations: `list_claims`, `get_claim`, `get_policy`, `get_claim_history`, `get_instructions` and `list_handlers`. The claim agent's instructions are `backend/instructions/claim.md`, served at `/api/instructions/claim`.
  - `backend/documents.py` splits the policy wording and the claims manual into numbered sections: `list_sections` (the contents of both), `search_documents` (the sections that best match a few words, each with its best line) and `read_section` (one section, headed such as `Claims manual, 9. Repeat claims`). The whole wording is no longer served.
  - The rules raise `backend.errors.NotFound` or `Refused`, which `backend/main.py` answers with 404 and 409; nothing else in the backend knows HTTP.
  - The rules are in `backend/rules.py`. `record_decision` takes approve, decline or refer. A decline or referral is decided with a payout of 0. An approval of $1,000 or less stays in progress until `pay_claim` pays it. An approval over $1,000 waits for sign-off: `pay_claim` is refused with 409 until `sign_off` records a handler. A sign-off doesn't pay: it moves the claim back to in progress for the agent to pay, and the payment records who signed off and when. `record_decision` and `pay_claim` return the claim, and a repeat of the same decision or payment counts as done; a different decision or amount is refused.
  - `backend/payouts.py` holds the payout rules from the Week 2 Day 1 lab. `calculate_payout` (`POST /api/policies/{policy_id}/payout`, with the benefit, the lines and what others paid) returns the calculation step by step, the payout and whether it needs sign-off, with the limit from `data/company.json`.
  - `add_step` and `list_steps` keep the agent's steps on a claim.
  - `backend/usage.py` records what the agent uses on each claim, with the run it happened in (or none, as on a resume after a sign-off): `record_model_call` (input and output tokens and OpenRouter's cost) and `record_work_time` (when a stretch of work started and how many seconds it took). It is the only module that touches the `model_calls` and `work_times` tables.
  - `backend/runs.py`: a run is a dispatch of the queue with N claim agents at once (`kind`, `agents`, `claim_set`, `tiny`, `model` and `reasoning_effort` are recorded). `create_dispatch` refuses while a run is running ("A dispatch or evaluation is already running"). `list_claims_to_work` gives the claims in progress first, then the waiting ones, each oldest submitted first. `take_claim` moves a waiting claim into the run with a new `thread_id`, or a claim in progress (left by a stopped dispatch) into the run on the same thread, so it carries on as the same attempt. `return_claim` follows a failed attempt: attempts plus one and the thread cleared, then back to `waiting`, or `needs_handler` after two. `finish_run` refuses while one of the run's claims is waiting. `stop_run` records the reason and leaves the claims as they are, for the next dispatch. `get_run` and `get_latest_dispatch` give the run with its claims (each with its model cost and working time in the run), a `RunSummary` built from the records (approved, declined and referred counts, each payout waiting for sign-off, the claims left for a handler and those still in progress), the run's model cost and its time. `get_latest_run` gives the latest run of any kind. One run at a time.
  - `start_dispatch` (`POST /api/dispatches/start`, with `agents` from 1 to 25) and `start_agent` on one waiting claim ask the agent's service to start, and write nothing first: the service creates the run. A refusal from the service comes back as a 409 with its reason, and a service that can't be reached as a 409, "The agent's service is not running". A restart of the backend doesn't touch runs or claims.
  - Evaluations, in `backend/evaluations.py`: `start_evaluation` (`POST /api/evaluations/start`, with `agents`, `claim_set` of `evaluation` or `held_out`, and `tiny`) asks the agent's service to start one, as a dispatch does. `create_evaluation`, which the service calls, creates the run (kind `evaluation`, with its set, `tiny`, N, the model and the reasoning effort) and a copy of each of the set's claims (all 25, or its five `tiny` ones), waiting, with a new id such as `RUN-0007-CLM-1001` written into its record, and the original's id in `copy_of`. Copies never show in `list_claims`, a dispatch never works them, and `sign_off` refuses one with "An evaluation's copy can't be signed off". An evaluation works only its own copies, through the same dispatcher and claim agent. `list_evaluations` (newest first) and `get_evaluation` give each evaluation with its measures and its copies scored.
  - `backend/scores.py` is the only module that reads the answer key. It scores each copy against the handler's decision, with the measures from the Week 2 Day 4 lab: `decision_accuracy` (the decisions match), `accuracy` (and the payouts are within a dollar), the cost of mistakes (a wrongful decline $1,500, a wrongful approval its payout, a needless referral $50, a wrong amount on a right approval the difference), the straight-through rate (the share not referred), the model cost per claim, the working time per claim and the run's time. A copy the agent didn't decide counts as a referral with no payout.
  - Seeding loads the held-out claims from `data/evals/held_out_claims.json` into `held_out_claims`, out of the queue, and the handlers' decisions on both labelled sets (`data/evals/decisions.json` and `held_out_decisions.json`) into `answers`: the set, the claim, the decision, the payout and `tiny`.
  - `backend/agent_service.py` is the backend's only way to the agent, at `UNDERCOVER_AGENT` (or `http://127.0.0.1:8002`). A sign-off asks it to resume the claim once the sign-off is saved; the sign-off stands if the agent can't be reached.
- `agent/`: the UnderCover Agent. The claim agent is a hand-written LangGraph graph on OpenRouter, saved after every step, and the dispatcher works a run's claims with up to N claim agents at once.
  - `agent/api.py` is the only way to the backend: one function per operation, with the base URL (`BACKEND_URL`, or `http://localhost:8000`) in one place. A 4xx raises `api.Refused`.
  - `agent/tools.py` holds the claim agent's eight tools, each one backend call, including the three document lookups and `calculate_payout`; it has no tool to pay, and none to start a run.
  - `agent/dispatcher.py` is the dispatcher, a LangGraph graph with no model, as in the Week 2 Day 4 lab: `list_claims` lists the run's claims to work, leaving out claims the service is resuming after a sign-off; the edge `fan_out` sends each to `work_claim` with one `Send` per claim; and `finish` finishes the run once every claim is back. `max_concurrency` is N. `work_claim` calls `harness.work_claim`, its only way to the claim agent, with a `RetryPolicy` on LangChain's `ModelRateLimitError` and `ModelTimeoutError` (3 attempts, the first wait 5 seconds), and an `error_handler` that leaves the claim in progress for the next dispatch when the retries run out, so no claim stops the dispatch. The dispatcher saves no progress of its own. If the dispatch itself fails, the run is stopped with the reason.
  - `agent/harness.py` holds the model, `openai/gpt-6-luna` with low reasoning effort, or `MODEL_NAME` if set with no reasoning effort (`model_settings()` gives the name and the effort, `none` for `MODEL_NAME`), and the claim agent's graph:
    - The nodes are `agent` (the model, with `RetryPolicy` retrying a failed call twice, and a count that raises past 30 model calls), `tools` (a `ToolNode` that hands a refused backend call back to the model as text), `check` (reads the claim back after `record_decision`), `sign_off` (waits on `interrupt()`) and `pay`.
    - After a decision the backend's status decides the way: `awaiting_sign_off` waits at `sign_off`, an approval in progress goes to `pay`, a decline or referral ends. The graph never compares a payout with the limit.
    - Every message, tool call and tool result is a step on the claim, and so are "Waiting for a handler's sign-off.", "Signed off by …" and "Paid $…".
    - The `agent` node records each reply's tokens and `usage.cost` (`response_metadata["token_usage"]["cost"]`) with `record_model_call`, and `run_claim` records each stretch of the graph's work with `record_work_time`, in a `finally`, so failed attempts count and a wait for a sign-off never does.
  - The checkpointer: each claim run gets a `PostgresSaver` of its own (`saver()`), since one saver holds a lock around every read and write, all on one pool per process (`pool()`) of at most 4 connections in the `undercover` schema, where a claim agent waits up to two minutes for a connection. Without `DATABASE_URL` every claim run shares one `InMemorySaver`. Every run uses `durability="sync"`. A claim's thread is its attempt's `thread_id`.
  - `run_claim(claim_id, thread_id, run_id)` starts a thread, carries on one stopped partway from its last step, or resumes one waiting for a sign-off once the sign-off is recorded. `work_claim(run_id, claim_id)` takes the claim into the run (posting "Agent started" on a new thread), runs it, and posts "Agent finished" once the claim has left `in_progress`. A rate limit or a timeout is raised with the claim still in progress, so the dispatcher's retry carries it on from its last saved step. Any other failure calls `return_claim`, and a claim back in the queue is tried once more on a new thread straight away. When an evaluation's copy is held for sign-off, its thread is deleted from the checkpointer, since nobody signs off a copy. It always answers in one line, such as `CLM-1001: approved, $420.00 paid`. `resume(claim_id)` picks a claim back up after its sign-off and pays it, with no run.
  - Every claim agent is traced in Langfuse when `LANGFUSE_PUBLIC_KEY` is set, in a session named after the claim and its thread, such as `CLM-1001 ac703c9a-…`, which holds the traces from before and after a sign-off, and tagged with its run's id, such as `RUN-0002`. Both are set with `propagate_attributes`, since a claim graph run inside the dispatcher's node is not the root of its trace, and Langfuse reads `langfuse_tags` in the metadata only at the root. Nothing loads `.env` in code: `npm run dev` and `npm run reset` pass it with `uv run --env-file .env`.
  - `agent/service.py` is the agent's service and its entry point, a small FastAPI app on port 8002 that `npm run dev` starts beside the backend and the dashboard. `start_dispatch` (`POST /dispatches`, with `agents`) and `work_one` (`POST /claims/{claim_id}/work`, a dispatch with N=1 on one claim) take the run lock without waiting, or answer 409 "A dispatch or evaluation is already running"; otherwise they answer 202, then create the dispatch through the backend with the model and its reasoning effort, and run the dispatcher in the background. `start_evaluation` (`POST /evaluations`, with `agents`, `claim_set` and `tiny`) does the same under the same lock, creating the evaluation and its copies through the backend; it never asks for the handlers' decisions. `resume_claim` answers 202 and resumes the claim in the background, keeping it in the set of claims dispatches leave out until it is done. When the service starts, it sets up the checkpointer's tables, waits for the backend, and stops the run it left running with "The agent's service restarted"; the next dispatch carries its claims on.
  - The claim agent's instructions are `backend/instructions/claim.md`: a goal, its rules and what done looks like, not a fixed order of work. Its work ends with its decision; the system pays.
- `dashboard/`: React, Vite and TypeScript in the UnderCover brand. The queue page has a count of claims in each state and the eight-column table. A claim page, opened from `#/claims/CLM-1001`, shows the summary, the decision and payment, the story, items, documents, policy and claim history. Light and dark start in the computer's setting. The "Dark mode" slider in the header, on every page, switches them and the browser remembers the choice (`localStorage` key `undercover-theme`); the mode is the `data-theme` attribute on `<html>`, set by a script in `index.html` before the page draws. `src/api.ts` holds the typed fetch functions.
  - The queue page's "Dispatch" panel (`RunPanel.tsx`) has "Claim agents at once" (1 to 25, starting at 3) and "Dispatch the queue", disabled while a dispatch is running or when no claim is waiting or in progress. A refusal shows its reason, such as "A dispatch or evaluation is already running" or "The agent's service is not running", marked with a bar in the alert color. It shows the latest dispatch: "Running, 3 claim agents at once", "Finished" or "Stopped" with the reason, each of its claims with a status chip and a link, its model cost and time ("Model cost $0.07, time 20 s", the dispatch's own time from start to finish), and once finished its summary from the records: "Approved 2, declined 1, referred 0.", each payout waiting for sign-off, and the claims left for a handler or still in progress. It polls every two seconds while the dispatch is running, and after a start until the new dispatch appears. The counts and chips include "Needs a handler".
  - A waiting claim has a "Run the agent" button. The claim page shows "Sections read", the first line of each `read` step such as "Claims manual, 9. Repeat claims" ("None yet." before any), and the agent's steps as a timeline (long tool results and sections read fold away) and polls every two seconds while the claim is in progress; the queue polls every two seconds.
  - A claim waiting for sign-off shows a "Payment on hold" panel with a handler picker and "Sign off and pay". Once paid, the decision panel shows the payment with its date and time and who signed off.
  - The "Color-blind mode" slider next to "Dark mode" switches the claim-state, decision and payment-on-hold colors to the Okabe-Ito palette and adds a check, cross or arrow to each decision chip (`data-colors` on `<html>`, key `undercover-colors`, off by default). The two sliders are independent. See `docs/ACCESSIBILITY.md`.
  - `#/instructions` shows the claim agent's instructions, read only, in one panel, "Working a claim".
- `e2e/`: Playwright tests on their own backend (port 8001, `e2e/e2e.db`, rebuilt by `backend.seed` at the start of each run) and their own Vite (port 5174), so they never touch the data from `npm run dev`. Their backend's `UNDERCOVER_AGENT` is a stand-in for the agent's service on port 8003, `e2e/agent-stand-in.mjs`, which answers 202 and lists what reached it at `/calls`, each with its body, such as `POST /dispatches {"agents":5}`; the tests act as the agent's service through the API.

## Claim states

| State | Meaning |
|---|---|
| `waiting` | In the queue, not yet worked |
| `in_progress` | The agent is working on it, or a handler has signed off and the agent is about to pay it |
| `awaiting_sign_off` | Approved over $1,000; the agent waits, and the payment is on hold, until a handler signs off |
| `decided` | Declined, referred, or approved and paid |
| `needs_handler` | Failed twice; left for a handler |

## Running it

- `npm run dev` starts the backend (8000), the agent's service (8002) and the dashboard (5173), passing `.env` to the backend and the agent.
- `uv run -m agent CLM-1001` starts a dispatch on one waiting claim through the backend's API, which hands it to the agent's service, so `npm run dev` must be up. It prints each change to the run's claims, then how the run ended, from its summary.
- `npm run reset` rebuilds the database from `data/`, on Supabase when `.env` has `DATABASE_URL`, where it drops the whole `undercover` schema, the agent's saved threads included: all 25 claims waiting. Stop `npm run dev` first. Run it once after pulling this build, since the tables changed.
- `npm run check` runs every check. `agent/tests/test_structure.py` and `backend/tests/test_structure.py` check the layout in `docs/CODE_STANDARDS.md`.

## Known issue

Stopping `npm run dev` sometimes leaves the agent's service holding port 8002, so the next `npm run dev` fails with "Address already in use". The service's worker exits, but uvicorn's `--reload` supervisor stays blocked on a lock: its SIGTERM handler calls `threading.Event.set()` while the main thread may hold the same event's lock in `Event.wait()`. This is in uvicorn 0.54.0's reloader, not in the product, and the service without `--reload` doesn't use it. Until it is settled, end the leftover process (on Linux or a Mac, `kill -9` the process listening on 8002).

## Commit guard

`.claude/settings.json` and `.claude/hooks/guard-commit.mjs` stop Claude Code from committing with `--no-verify`, `git commit -n`, `LEFTHOOK=0` or `core.hooksPath`. Blocks go to `~/.claude/blocked-commits.log`, and every `git` command it sees goes to `~/.claude/guard-calls.log`.
